# Priority-with-retry 3.1 Notes

Updated: 2026-07-24  
Mode: Standard

## Key Changes

- Moved version details out of the policy XML and into this release note.
- Centralized inbound initialization and error-response calculations.
- Expanded successful-response handling while preserving the PTU empty-200 retry workaround.

## Improvements

- Acquires a Managed Identity token only when the model has an MI backend.
- Preserves backend error bodies and `Content-Type` values for permanent `4xx` responses.
- Uses `retry-after-ms` first, then `retry-after`, then `defaultRetryAfter`; backend delays retain the two-second safety buffer.
- Defaults missing, non-numeric, and out-of-range request priorities to priority `3`.
- Treats missing, empty, or unparsable `acceptablePriorities` values as allowing priorities `1`, `2`, and `3`.

## Bug Fixes

- Treats `400` as permanent except for `context_length_exceeded`, which remains eligible for failover.
- Clears `Authorization` and `api-key` before applying the selected backend authentication mode.
- Treats completed responses from `200` through `399` as successful instead of retrying valid non-200 responses.
- Bounds empty-200 retries by the configured backend-call budget.

## Refactor

- Consolidated inbound calculations in `initObj`, then publishes runtime variables together.
- Consolidated final error classification and response/header formatting in `onErrorObj`.
- Preserves `responseObject` for inherited `on-error` policy compatibility.
- Clarified that `retryCount` is the number of actual backend calls; policy-loop cycles without a call do not consume it.
